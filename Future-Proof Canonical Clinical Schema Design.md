Strategic Architecture Report: Designing a Future-Proof Canonical Clinical Schema for MVP Healthcare ProductsExecutive SummaryThe development of a Minimum Viable Product (MVP) in the healthcare technology sector presents a fundamental architectural tension. Engineering teams must balance the need for rapid application iteration against the strict, highly normalized data exchange requirements of modern healthcare ecosystems. A central challenge involves structuring clinical information so that it remains lightweight enough for early-stage development while ensuring seamless eventual integration with Hospital Information Systems (HIS) and Electronic Health Records (EHR) via the Health Level Seven Fast Healthcare Interoperability Resources (HL7 FHIR) standard. Storing clinical narratives exclusively as unstructured free-text notes fundamentally limits a product’s lifecycle, creating a "dead-end" data model that cannot be mapped to semantic interoperability standards and fails to support downstream clinical decision support or analytics.The recommended architectural approach is the implementation of a "FHIR-Informed Internal Model combined with a Facade Pattern". Under this paradigm, the MVP should not attempt to implement a native FHIR server or store raw FHIR resources as its primary relational database schema. Pure FHIR data models are inherently designed for data exchange, not for optimized transactional storage, making them overly complex for MVP domain logic. Instead, the MVP must adopt a simplified Canonical Clinical Schema that utilizes foundational FHIR data types embedded within flat, denormalized database records optimized for application querying.This strategy ensures that when HIS API integration becomes necessary, the canonical model can dynamically map to FHIR R4 (the current industry baseline) or FHIR R5 without requiring a catastrophic schema migration. The canonical schema will support structured clinical observations, longitudinal condition tracking, diagnostic reporting, and medication histories alongside narrative texts, preventing the architectural trap of treating the medical record as a disconnected series of text blobs. By implementing standard terminologies and tracking provenance at the schema level, the product remains agile yet fully prepared for enterprise interoperability.Architectural Foundations and Security ConsiderationsDesigning a clinical data repository requires addressing security, privacy, and auditability at the foundational schema layer. Healthcare data is legally protected and highly regulated; thus, losing authorship or timestamp information is a critical failure. The architectural design must support rigorous tracking of who accessed or modified data and when these actions occurred.At the schema level, every canonical entity must incorporate an embedded audit and provenance metadata structure. While FHIR defines standalone AuditEvent and Provenance resources, generating these synchronously during MVP development introduces unnecessary complexity. Instead, the canonical database schema should utilize _history tables or an event-sourcing paradigm. For instance, architectures like Aidbox utilize a txid (transaction ID) and cts (creation timestamp) across all resource tables, shifting previous versions into history tables upon update or deletion. This ensures that every modification is logged, allowing the system to construct formal FHIR Provenance and AuditEvent records retroactively when required by integration partners.Multi-tenancy and data isolation must also be considered. If the MVP serves multiple clinics or hospital systems, the schema must include logical tenant isolation (e.g., a tenantId field on every table or row-level security policies in PostgreSQL). This prevents cross-contamination of patient records, a vital security consideration that simplifies compliance audits.Clinical Workflow and FHIR Resource Semantic AnalysisTo design a highly effective canonical schema, the underlying clinical purpose and boundaries of the target FHIR resources must be strictly defined. HL7 FHIR differentiates resources based on clinical intent, workflow state, and provenance. Misunderstanding these semantic boundaries results in flawed data models that fail interoperability certification.Patient, Practitioner, and Encounter DynamicsThe Patient resource serves as the central subject of the clinical record, capturing longitudinal demographic and administrative identifiers. Systems must preserve external identifiers, such as national identity numbers or hospital-issued medical record numbers, to resolve identities across disparate systems without generating duplicates. The Practitioner resource represents the clinician or user providing care, which must be distinctly separated from the Person resource (which may link multiple personas) or RelatedPerson (family members).The Encounter resource acts as the episodic glue, representing a specific interaction between a Patient and a Practitioner within a given timeframe and location. A pervasive anti-pattern in early-stage health tech is attaching episodic clinical findings directly to the Patient without an Encounter reference. This destroys the temporal clinical context required by billing and care continuity systems. Differentiating between encounter-level data (data pertinent only to the current visit, such as a localized physical exam) and patient-level longitudinal data (data that persists across visits, such as a chronic diagnosis) is crucial.Condition versus ObservationThe boundary between Condition and Observation is frequently misunderstood by engineering teams. An Observation represents a discrete, point-in-time assertion, measurement, or symptom. Examples include a blood pressure reading of 120/80, a patient-reported fever spike, or a clinician observing unintended weight loss. Conversely, a Condition represents a clinician's formalized diagnostic interpretation or a longitudinal problem, such as Essential Hypertension or Type 2 Diabetes Mellitus, that often accounts for the underlying observations. The canonical model must separate transient symptoms (Observation) from established problem list items (Condition), though both should be conceptually linked to demonstrate diagnostic evidence.DiagnosticReport versus ObservationWhile an Observation holds a single atomic result, a DiagnosticReport serves as the clinical grouping and contextual wrapper for a suite of observations. For example, a Complete Blood Count (CBC) or a metabolic panel is a single DiagnosticReport containing multiple nested Observation resources, representing hematocrit, hemoglobin, and platelet counts. The report provides the status, the ordering clinician, the interpretation, and often a narrative conclusion or an attached PDF. Confusing the two leads to data fragmentation where related lab values lose their overarching interpretive context.MedicationRequest versus MedicationStatementThe FHIR pharmacy module heavily relies on intent to govern resource usage. A MedicationRequest is an actionable order or prescription instructing a pharmacy to dispense or a nurse to administer a specific drug. A MedicationStatement—which transitions conceptually to MedicationUsage in FHIR R5—is a declarative assertion that a patient is taking, has taken, or plans to take a medication. This is often based on patient self-reporting, medication reconciliation, or historical intake. For an MVP, separating these concepts is vital to prevent patient-reported vitamin supplements from being mistakenly processed and transmitted as active HIS orders.Composition versus DocumentReferenceWhen bridging structured data with narrative notes, FHIR offers Composition and DocumentReference. A Composition is a highly structured, self-contained clinical document (analogous to a Clinical Document Architecture or CDA document) consisting of specific narrative sections, authors, and attestations, which actively embeds or references discrete resources. A DocumentReference points to an external file, such as a scanned PDF, an audio recording, or a plain text note, acting as metadata for a binary payload. For an MVP, standard clinical notes authored within the system should be modeled using a structured format capable of exporting as a Composition, whereas external file uploads must map to DocumentReference.AllergyIntoleranceThis resource is dedicated exclusively to recording clinical allergies and intolerances, tracking the offending substance, the criticality, and the manifestation of adverse reactions. It is distinct from an AdverseEvent, which records an actual incident of patient harm that has occurred within a clinical setting.Terminology and Code-System ConsiderationsA canonical schema is rendered useless if it relies entirely on local strings for clinical concepts. Terminology normalization is the bedrock of interoperability. The schema must utilize the CodeableConcept primitive, which allows a single clinical concept to carry a human-readable text string alongside one or more machine-readable codes from standard systems.The system should enforce or recommend the following vocabularies based on the domain:SNOMED CT: The preferred terminology for broad clinical findings, Condition resources (diagnoses), procedures, and the substances in AllergyIntolerance.LOINC: The mandatory terminology for identifying laboratory tests, vital signs, and document types (e.g., categorizing a clinical note as a Discharge Summary).RxNorm and ATC: The required coding systems for medications, capturing precise drug formulas, dosages, and active ingredients.ICD-10: Primarily used for billing and epidemiology. Diagnoses can be dual-coded with both SNOMED CT for clinical specificity and ICD-10 for administrative routing.Custom/Local Codes: If an MVP must rely on internal hospital codes, the schema handles this by setting the system property of the Coding object to a custom URI (e.g., http://hospital.local/codes/labs) while preserving the raw input in the text field.FHIR Resource Research TableThe following table synthesizes the architectural requirements for mapping canonical elements to the 11 core FHIR resources, balancing MVP simplicity with future HIS integration. This mitigates the complexity of direct FHIR interactions while enforcing semantic discipline at the application layer.TypeScript// --- Foundation FHIR Primitives ---

export interface Coding {
  system?: string; // Standard terminology URI (e.g., 'http://snomed.info/sct')
  code?: string;   // Machine-readable code (e.g., '38341003')
  display?: string;// Human-readable name of the code
}

export interface CodeableConcept {
  coding?: Coding;
  text?: string;   // Crucial for MVP: stores the clinician's exact free-text if a terminology code is unknown
}

export interface Identifier {
  use?: 'usual' | 'official' | 'temp' | 'secondary' | 'old';
  system?: string; // Issuer namespace URI
  value: string;   // The actual ID string (e.g., MRN, NPI)
}

export interface HumanName {
  use?: 'usual' | 'official' | 'temp' | 'nickname' | 'anonymous' | 'old' | 'maiden';
  text?: string;   // Full name string
  family?: string; // Surname
  given?: string;// Array of first and middle names
  prefix?: string;
  suffix?: string;
}

export interface Reference {
  reference: string; // Format: "ResourceType/id" (e.g., "Patient/123")
  type?: string;     // The target entity type
  display?: string;  // Human-readable summary
}

export interface Period {
  start?: string; // ISO 8601 DateTime
  end?: string;   // ISO 8601 DateTime
}

export interface Quantity {
  value: number;
  unit: string;   // Human-readable unit
  system?: string;// e.g., 'http://unitsofmeasure.org' (UCUM)
  code?: string;  // UCUM machine code
}

export interface AuditMetadata {
  createdAt: string;
  updatedAt: string;
  createdBy: Reference; // Points to the Practitioner performing the action
  updatedBy: Reference;
  versionId: number;    // Supports retrospective Provenance tracking
}

// --- Canonical Domain Entities ---

export interface CanonicalPatient {
  id: string;
  identifiers: Identifier;
  names: HumanName;
  gender: 'male' | 'female' | 'other' | 'unknown';
  birthDate?: string; // YYYY-MM-DD
  telecoms: any;    // ContactPoint array (email, phone)
  audit: AuditMetadata;
  // Denormalized fields for quick MVP database searching without parsing JSON arrays
  searchName?: string; 
}

export interface CanonicalClinicalNote {
  id: string;
  subject: Reference;    // -> Patient
  encounter?: Reference; // -> Encounter
  type: CodeableConcept; // e.g., LOINC code for "Discharge Summary"
  status: 'preliminary' | 'final' | 'amended' | 'entered-in-error';
  title: string;
  sections: Array<{
    title: string;
    code?: CodeableConcept;
    text: string;        // HTML, Markdown, or raw text narrative
    entries?: Reference; // Loose links to discrete Observations/Conditions derived from this specific text section
  }>;
  audit: AuditMetadata;
}

export interface CanonicalMedication {
  id: string;
  subject: Reference;
  // This flag controls routing during export: 'order' -> MedicationRequest, 'history' -> MedicationStatement
  assertionType: 'order' | 'history'; 
  status: 'active' | 'completed' | 'entered-in-error' | 'stopped';
  medication: CodeableConcept; // e.g., RxNorm codes
  dosageText: string; // MVP simplification over complex FHIR Dosage structures
  period?: Period;
  audit: AuditMetadata;
}

Clinical findings, interventions, and aggregations (such as the ClinicalNote and DiagnosticReport) link inherently to the patient, optionally to the encounter, and systematically reference one another to maintain the integrity of the clinical narrative.MVP Implementation Recommendation: A Staged RoadmapImplementing a robust, fully compliant interoperability layer from day one overburden engineering teams and stifles MVP agility. A phased, systematic approach is necessary to mature the architecture.Stage 1: MVP Schema without HIS IntegrationDeploy the canonical schema using a mature relational database, such as PostgreSQL. Leverage advanced JSON functionality (like JSONB) for storing nested FHIR primitives (CodeableConcept, Identifier) while extracting denormalized search fields (e.g., searchName, patientId) into standard columns for indexing. The user interface must support free-text entry but store it exclusively within the CodeableConcept.text field, ensuring the schema is structurally ready for future coding while eliminating immediate terminology mapping overhead.Stage 2: Terminology Normalization and CodingIntroduce background terminology mapping to enrich the data. While the clinician inputs free text, the backend asynchronously queries terminology servers (via FHIR $expand and $translate operations) to append standardized SNOMED CT, LOINC, and ICD-10 codes into the CodeableConcept.coding arrays. This ensures the MVP’s data is semantically rich and analytically viable before attempting external integration.Stage 3: FHIR-Compatible Export (Egress)Implement outbound mapping algorithms that translate the Canonical database records into valid FHIR JSON payloads, formatted as FHIR Bundles. For instance, a CanonicalClinicalNote is exported as a Composition resource, bundled alongside its referenced Patient, Encounter, and discrete Observation resources, mimicking a standard document exchange profile.Stage 4: Bi-Directional HIS/EHR API Integration (Ingress)Integrate with major hospital EHRs (e.g., Epic, Cerner) using SMART on FHIR protocols. Implement a robust anti-corruption layer (Facade) that intercepts inbound FHIR REST API calls, mapping external FHIR resources down into the internal canonical schema. This layer must gracefully handle differences between FHIR versions, such as resolving the transition of MedicationStatement to R5's MedicationUsage, shielding the MVP's core application logic from upstream FHIR volatility.Anti-Patterns and Architectural RisksDesigning healthcare systems demands avoiding pervasive industry anti-patterns that routinely lead to data lock-in and interoperability failure. Engineering teams must monitor for the following structural mistakes:The "Free-Text Only" Trap: Storing clinical notes strictly as raw strings in a simple database column is catastrophic. Without a mechanism to map narrative texts into discrete Condition or Observation elements, the resulting data cannot trigger clinical decision support (CDS) alerts, satisfy EHR quality reporting, or be queried analytically. The mitigation is enforcing the structured CanonicalClinicalNote format.Mixing Encounter-Level and Patient-Level Data: Recording episodic data, such as a daily blood pressure reading, without linking it to the specific clinical Encounter strips the data of its temporal context. Conversely, tying longitudinal conditions, like a lifelong allergy, strictly to a single encounter prevents it from surfacing on the patient's global profile.Treating Uploaded PDFs as the Only Clinical Record: Relying solely on DocumentReference wrappers for PDFs prevents the host system from executing discrete queries (e.g., "Find all patients with an HbA1c > 7.0"). PDFs should supplement, not replace, structured Observation entries.Conflating Diagnostic Reports with Observations: Attempting to store a complex lab panel, such as a liver function test, as a single Observation with a massive text blob packed inside valueString violates FHIR constraints. A DiagnosticReport must be used to conceptually group multiple discrete Observation resources.Failing to Preserve External Identifiers: Overwriting a patient's Hospital Medical Record Number (MRN) with the MVP’s internal database UUID guarantees that data exported back to the EHR will fail to match the correct patient record. The Identifier array must be utilized relentlessly across all entities.Hardcoding Local Clinical Terms Without Code-System Support: Creating drop-down menus with arbitrary string values (e.g., "High Blood Pressure") instead of binding them to standard terminology codes (e.g., SNOMED CT 38341003) prevents the data from being understood by receiving systems.Not Separating Medication Requests from Medication History: Combining active pharmacy prescriptions and self-reported medication histories into a single table without an intent flag (assertionType) creates severe clinical risk, potentially causing duplicate dispensing or inaccurate clinical reconciliation.Losing Provenance and Authorship: Healthcare data constitutes a legal record. Failing to log exactly who authored a change and when it occurred compromises patient safety and violates HIPAA and GDPR audit requirements. AuditMetadata must be attached to every canonical entity to prepare for future FHIR AuditEvent and Provenance generation.Final Architecture Decision Record (ADR)Decision: Adopt a "FHIR-Informed Internal Model combined with a Facade Pattern" architecture utilizing a Canonical Clinical Schema for the MVP, deliberately rejecting both a native FHIR server deployment and a proprietary, unstructured database schema.Rationale: Native FHIR servers introduce severe overhead in querying, validation, and domain logic handling that stifles rapid MVP development. Conversely, entirely custom unstructured models result in a technical debt spiral when HIS API integration is inevitably required. Using FHIR primitives (CodeableConcept, Reference) inside flat, denormalized canonical entities provides a mathematically proven compromise that accelerates development without sacrificing interoperability.Consequences: The engineering team must write and maintain a mapping layer that translates between the Canonical Schema and HL7 FHIR (R4/R5). While application queries will be significantly faster and domain logic cleaner, the system will rely heavily on these mappings to maintain interoperability compliance.Trade-offs: A slightly increased upfront design complexity—such as implementing nested CodeableConcept objects instead of simple string columns—is traded for massive long-term integration viability and immunity against minor FHIR version updates and breaking changes.What to Implement Now: Build the relational database schema leveraging JSON indexing capabilities for FHIR primitives. Implement CanonicalPatient, CanonicalEncounter, CanonicalObservation, CanonicalCondition, and the dual-intent CanonicalMedication. Ensure all narrative is stored in structured CanonicalClinicalNote objects to facilitate future export as FHIR Composition resources. Implement robust AuditMetadata across all tables.What to Defer: Defer active, bi-directional RESTful FHIR integration, SMART on FHIR authentication routing, native Provenance resource generation, and strict FHIR profile validation until post-MVP phases. Focus entirely on establishing semantic discipline and data integrity through the canonical schema.
